# P0：预制作冻结

| 项目 | 内容 |
| :--- | :--- |
| 日期 | 2026-08-10 至 2026-08-23 |
| 时长 | 2 周 |
| 阶段目标 | 把完整愿景收束为第一批可开发范围，冻结 MVP 方向、数据结构和灰盒资源标准。 |
| 阶段结果 | 团队可以直接进入原型开发，不再争论第一版做哪些内容。 |

---

## 一、阶段目标

P0 不制作大规模可玩内容。它的核心价值是确定边界：

- 第一版只验证“规则收集 + 背包构筑 + 自动战斗 + 短探索”。
- 第一版内容只覆盖太玄宗、地下灵脉、荒古城和落星谷。
- 所有系统先为 P1 和 P2 服务，不提前实现完整大世界。
- 所有配置先能被程序读取和调试，再追求策划工具便利性。

## 三、设计细化

### 3.1 MVP 范围

| 类型 | 范围 |
| :--- | :--- |
| 主线 | 太玄宗灭门、地下灵脉逃生、荒古城调查、落星谷首领。 |
| 主角 | 叶凡固定身份，暂不开放外观自定义。 |
| 伙伴 | 沈青萝进入战斗与剧情，但羁绊只做基础记录。 |
| 地图 | 节点式探索，不做完整开放世界。 |
| 天命格 | 只实现倍增模式，百分比和复制只做数据预留。 |
| 规则 | 先做 12 条基础规则，覆盖触发、条件、效果和代价。 |

### 3.2 首批规则方向

| 类别 | 数量 | 示例 |
| :--- | :--- | :--- |
| Trigger 触发 | 3 | 战斗开始、击杀、受伤。 |
| Condition 条件 | 3 | 相邻同类、生命低于阈值、目标带有破甲。 |
| Modifier 修正 | 3 | 增加次数、扩大范围、提高持续时间。 |
| Transform 转化 | 2 | 丹药转护盾、星核转剑气。 |
| Cost 代价 | 1 | 消耗灵气或污染一格背包。 |

### 3.3 首批道具方向

| 类别 | 数量 | 用途 |
| :--- | :--- | :--- |
| 法器 | 6-8 | 支撑剑意、破甲和爆发。 |
| 符箓 | 5-6 | 支撑触发、连锁和控制。 |
| 丹药 | 4-5 | 支撑恢复、护盾和持续效果。 |
| 材料 | 6-8 | 支撑融合、转化和探索事件。 |
| 阵盘 | 2-3 | 支撑规则连接和位置收益。 |

## 四、技术细化

| 模块 | P0 决策 | 输出 |
| :--- | :--- | :--- |
| 数据加载 | 使用 JSON 作为首批静态配置格式。 | `items.json`、`rules.json`、`enemies.json` 字段说明。 |
| 背包网格 | 先按 8x6 设计，P1 可用 6x4 快速试验。 | 网格坐标、占格、旋转和特殊格规则。 |
| 规则引擎 | 规则拆为触发、条件、效果、代价。 | 规则执行顺序和冲突处理草案。 |
| 战斗 | 先做确定性模拟，后续再加入随机波次。 | 角色、敌人、技能、日志的最小数据结构。 |
| 存档 | P1 可暂用内存状态，P2 必须落盘。 | 存档字段预留清单。 |

## 五、美术与表现细化

P0 只制定灰盒资源标准：

- 背包格使用清晰色块区分普通格、特殊格、污染格和不可用格。
- 道具图标先使用形状和颜色，不等待正式美术。
- 战斗角色先用简化剪影，重点表现攻击范围、命中和规则触发。
- 规则触发必须有统一视觉标识，例如边框闪烁、连线高亮、日志条目。
- P1 不追求角色立绘、完整地图背景和高规格特效。

---

## 六、验收标准

- MVP 功能清单、首批规则表、首批道具表、首批敌人表全部完成。
- P1 开发任务能拆到 1-3 天粒度。
- 技术知道第一批场景、脚本和数据文件的放置位置。
- 策划能新增道具和规则，不需要修改程序逻辑。
- 美术知道哪些是灰盒资源，哪些不需要在 P1 完成。

---

## 七、交接到 P1 的条件

P0 结束时，P1 必须可以立即开始以下任务：

1. 创建主场景和背包网格场景。
2. 读取首批道具和规则配置。
3. 拖拽物品并计算相邻关系。
4. 在灰盒战斗中触发至少 3 条规则。
5. 输出战斗日志和临时结算。
