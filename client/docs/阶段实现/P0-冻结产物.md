## 一、MVP 功能边界

P0 冻结的首个可玩闭环是：

`探索节点 -> 获取道具/规则 -> 整理背包 -> 自动战斗验证 -> 查看日志与结算 -> 选择下一节点`

| 模块 | P1 必须实现 | P1 明确不做 |
| :--- | :--- | :--- |
| 背包 | 6x4 原型网格、占格、拖拽、旋转、交换、相邻判定、1 个固定天命格 | 多页背包、筛选、自动整理、复杂污染 |
| 道具 | JSON 加载、形状、标签、基础效果、稀有度 | 强化、耐久、套装、随机词缀 |
| 规则 | 触发、条件、效果、代价、次数限制、执行日志 | 可视化规则编辑器、跨战长期规则、复杂递归链 |
| 战斗 | 确定性自动攻击、生命/护盾/资源、事件队列、胜负结算 | 复杂 AI、地形、伙伴羁绊、正式演出 |
| 探索 | 3-5 个节点、战斗/奖励/选择/首领节点 | 开放世界、动态天气、阵营路线 |
| 状态 | P1 使用内存状态，启动时允许重置 | 正式存档、迁移、云同步 |

## 二、首批地点与流程

| 顺序 | 地点 | P1 用途 | P2 扩展 |
| :--- | :--- | :--- | :--- |
| 0 | 玄离王府地窖 | 只保留剧情数据，不制作场景 | 序章残忆与身份伏笔 |

| 2 | 地下灵脉 | P1 主灰盒区域，完成教学与普通战 | 残阵岔路和精英战 |

P1 的短循环优先使用地下灵脉和落星谷，不要求把五个地点串成完整剧情流程。

## 四、运行时执行约定

1. 加载阶段先验证 `schema_version`、重复 ID 和必填字段，再建立只读 ID 索引。
2. 背包坐标以左上角为原点，先完成旋转归一化，再检查边界与占用。
3. 战斗事件按“触发事件 -> 筛选规则 -> 检查条件 -> 支付代价 -> 应用效果 -> 写入日志”执行。
4. 同一事件中的规则按背包格从上到下、从左到右排序；同一格按规则 ID 排序，保证结果可复现。
5. 连锁规则必须携带 `chain_depth`，超过规则限制时终止并记录日志，防止递归触发。
6. 未知枚举或未知效果类型视为配置错误；开发版本显示明确错误，不静默猜测行为。

## 五、灰盒界面标准

| 对象 | 表现约定 |
| :--- | :--- |
| 普通格 | 中性灰底和 1 像素边线 |
| 天命格 | 金色边框；触发时同步高亮道具、格子和日志 |
| 污染格 | 暗红斜纹；P1 仅用于首领机制演示 |
| 可放置预览 | 绿色覆盖；冲突或越界使用红色覆盖 |
| 道具类别 | 法器、符箓、丹药、材料、阵盘使用五种固定类别色 |
| 规则反馈 | 来源、目标和规则日志必须在同一时刻可辨认 |

灰盒资源只服务交互辨识，不等待正式立绘、地图背景和特效。

## 七、P0 验收结论

- MVP 功能边界、首批地点、规则、道具、敌人和节点数据已经冻结。
- 场景与脚本目录职责已经确定，P1 可直接创建 Godot 资源。
- P1 任务已拆到 1-3 天粒度，并覆盖 2026-08-24 至 2026-09-20。
- P0 只冻结数据合同和开发入口；玩法乐趣是否成立仍必须由 P1 可玩版本验证。
